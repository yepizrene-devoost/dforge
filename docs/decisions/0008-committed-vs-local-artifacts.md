# 0008 — Committed versus machine-local generated artifacts

- **Status:** accepted
- **Date:** 2026-10 (design phase)

## Context

A generated artifact is only useful if the right people receive it. Two failure
modes are visible in the workspace today:

**A machine-local file that looks committed.** `.atl/skill-registry.md` is
generated by scanning the local machine — every developer's `Sources scanned`
list and skill paths differ. It is ignored through `.atl/.gitignore`, whose only
content is `*`. But **a `.gitignore` cannot ignore itself**, so that file is never
committed either, and a fresh clone has no ignore rule at all: the local directory
reappears as untracked noise on every developer's machine. The rule has to live in
the root `.gitignore`.

**Committed memory that the harness never requires.** Covered in
[0003](0003-persistent-memory-and-branch-notes.md): `MEMORY.md` must travel with
the repository because the reader lacks the author's local tooling.

Both are the same question: does this artifact describe **the project**, or
**one developer's machine**?

## Decision 1 — Every generated path is classified

| Class | Meaning | Delivery |
| --- | --- | --- |
| `committed` | describes the project; a teammate needs it | written to the repository |
| `local` | describes this machine or this session | written to the root `.gitignore` |

Classification is fixed, not configurable, and follows one test:

> **Would a teammate cloning the repository be worse off without it?** Yes means
> committed. No means local.

## Decision 2 — The classification

| Path | Class | Why |
| --- | --- | --- |
| `AGENTS.md` | committed | the contract |
| `.dforge.yaml` | committed | single source of truth |
| `.agents/harness/**` | committed | the rules |
| `.agents/MEMORY.md` | committed | the reader has no local tooling |
| `docs/**` | committed | documentation and branch notes |
| `.agents/skills/**` | committed | project knowledge, authored for the project |
| `.agents/workflows/dflow.md` | committed | generated by `dflow`, not by `dforge` |
| `.atl/**` | **local** | machine-scanned index; paths differ per developer |
| `.env` | **local** | secrets |
| `/dist/`, `/bin/`, the binary | **local** | build output |
| `CHANGELOG.draft.md`, `RELEASE_NOTES.md` | **local** | regenerable; curated into `CHANGELOG.md` |

The last row is the organization's existing convention, kept as is: `dflow` and
the Go TUI CLI generate both files from Make targets and neither is committed.

## Decision 3 — `dforge` owns a delimited region of the root `.gitignore`

During generation and adoption, `dforge` maintains its `local` entries inside
comment markers, exactly as it owns a block of `AGENTS.md`:

```gitignore
# >>> dforge:local >>>
.atl/
.env
/bin/
/dist/
/dforge
*.exe
# <<< dforge:local <<<
```

Consequences of using markers here rather than appending:

1. **Adoption does not fight the project.** A repository with its own
   `.gitignore` keeps every existing line; `dforge` adds its region and replaces
   only that region on later syncs.
2. **Removal is possible.** Deleting the region removes exactly what `dforge`
   added, which is what makes adoption reversible without manual archaeology.
3. **No reliance on a nested self-ignoring file.** The root is the only place a
   rule can be relied upon, because it is the only one guaranteed to be present
   after a clone.

This is the same semantic `dforge` already reuses for `AGENTS.md`
([0001](0001-scope-and-ownership.md)), applied to the third file class it
co-owns.

## Decision 4 — `dforge check` validates the ignore region

`check` verifies that every path classified `local` appears in the region, that
the region is not duplicated, and that nothing classified `committed` was
accidentally added to it. A committed artifact that is silently ignored is a
failure that only surfaces when a teammate cannot find a file they were told
exists — the most expensive way to discover it.

## Open

1. **Editor and IDE directories.** `.DS_Store` is in the organization's
   convention; `.vscode/` and `.idea/` are not. Recommendation: leave them out of
   the generated region. Ignoring `.vscode/` can destroy settings a team intends
   to share, and it is a personal preference rather than a project fact. A project
   that wants them add them outside the `dforge` markers, where `dforge` will not
   touch them.
2. **`.agents/skills/**`.** Classified `committed` because skills are authored
   knowledge. Verify before implementation that no generated `SKILL.md` embeds an
   absolute local path; if one does, that file is `local` and the skill needs
   splitting.

## Consequences

- `dforge` now co-owns three files rather than two: `AGENTS.md`, `.dflow.yaml`
  (read-only), and the root `.gitignore`.
- Adoption must treat a pre-existing `.gitignore` entry that duplicates a
  `dforge` region entry as `identical`, not as a reason to fail.
- This record closes a gap: the ignore policy was unspecified in decisions 0001
  through 0007, which meant the first generated repository would have committed a
  machine-local index or lost it silently.

## Evidence

- `.atl/.gitignore:1` — a single `*`; the file cannot ignore itself, so it never reaches a clone.
- `git check-ignore -v .atl/skill-registry.md` on this repository resolves to `.atl/.gitignore:1:*` — the ignore works locally and would not exist after a fresh clone.
- `.gitignore` in the Go TUI CLI and `.gitignore` in `dflow` — near-identical conventions, including the `# Local Pi runtime state` comment, `.atl/`, `.env`, `/bin/`, `/dist/`, `.DS_Store`, and the regenerable release documents.
- `pkg/agent/reference.go:16-17` — the marker semantics reused for the ignore region.
