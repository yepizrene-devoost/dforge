# 0005 — `.dforge.yaml` configuration schema

- **Status:** accepted
- **Date:** 2026-10 (design phase)

## Context

Root-level configuration files are already the norm in this workspace:
`.dflow.yaml` (17 files), `boost.json`, `opencode.json` (325 lines in
a Laravel API and web application), `cliff.toml`, `components.json`, `.codex/`, and
`openspec/config.yaml`. The problem is not the number of dotfiles; it is that
there is no agreed **layout** — rule content lives in six competing places
(`.agents/workflows/`, `.agents/quality/`, `.agents/rules/`, `.ai/rules/`,
`.antigravity/`, and root `rules.md` / `style.md`).

## Decision — one configuration file at the repository root

`.dforge.yaml` is the sole source of truth. Every other artifact `dforge` produces
is generated from it.

### Rejected: a configuration section inside `AGENTS.md`

The alternative is attractive because it adds no file. It fails for four concrete
reasons:

1. **`AGENTS.md` is multi-writer.** `dflow` injects its reference block, Laravel
   Boost injects `<laravel-boost-guidelines>` (a ~230–310-line block; see
   `AGENTS.md:26-231`, in the Laravel application that keeps per-concern quality rule files), and humans add local rules. Putting parseable
   configuration there couples the schema to another tool's rewrite cycle.
2. **Not parseable without parsing markdown.** No CI job, hook or editor plugin
   can read it reliably.
3. **Generated files already reach several hundred lines.** The Laravel application that keeps per-concern quality rule files is 231 lines
   before local rules; a Laravel + Inertia application under company project management is ~310. Configuration buried inside that is
   configuration nobody reads.
4. **It has no precedent here.** `.dflow.yaml` already established the pattern
   and is understood by the team.

### Rejected: several dotfiles, one per concern

Splitting into `.dforge.policies.yaml`, `.dforge.memory.yaml` and similar
re-creates the fragmentation the tool exists to remove, and makes "what does this
project declare?" unanswerable without reading the whole set.

## The schema

```yaml
# .dforge.yaml — generated by 'dforge init'
version: 1

project:
  name: the Go TUI CLI
  organization: <org-slug>          # <org-slug> | autonomous
  management: autonomous         # jira | github | autonomous          (0002)
  ticket_prefix: null            # required when management: jira

harness:
  preset: go-cli                 # laravel-modern-web | laravel-api | go-cli
                                 # flutter-mobile | react-spa | astro-site
  discipline: iterative          # prd-first | iterative               (0004)
  domains: true
  branch_notes: true

memory:                          #                                     (0003)
  committed: required            # always; not a choice
  committed_path: .agents/MEMORY.md
  content: decisions             # not a changelog
  self_contained: true
  max_lines: 400
  local:
    hint: auto                   # detected at runtime, never required

policies:
  solid: strict
  acid: strict
  tdd: strict
  review_budget:
    commit_functional_lines: 600 # excludes docs, comments, formatting
    pr_slice_lines: 400
    file_lines_cap: 2000
  required: [solid, acid, tdd, memory, branch_notes, commit_format]

commits:
  format: derived                # derived from project.management
  language: en
  allow_paths_in_body: false

branches:
  provider: dflow | none         # none = the project runs its own flow
  base_branch_edits: forbidden   # the invariant only, never branch names

rollout:
  mode: enforced | advisory      # advisory reports without blocking
  owner: <name>                  # accountable for the rollout
  review_by: 2027-04             # REQUIRED whenever mode is advisory
  reason: "<why the window is needed>"   # REQUIRED on any renewal
```

## Three kinds of field, with different rules

| Kind | Rule | Examples |
| --- | --- | --- |
| **Declared** | The human answers during onboarding; `dforge` stores it | `project.management`, `harness.preset`, `harness.discipline` |
| **Derived** | Computed from a declared field; declaring it directly is an override, and a contradictory override is an error | `commits.format` from `management`; `memory.committed_path` from `discipline` |
| **Forbidden** | Cannot be expressed here at all | branch names and bases (`dflow`'s), Engram availability (developer-local), local paths |

The third row is the important one. A schema that can express branch names would
immediately become a second source of truth for a fact `dflow` already owns, with
the drift the inventory measured. The schema deliberately **cannot** say
`main`, `develop` or `uat`.

## Validation rules for `dforge check`

1. `management: jira` without `ticket_prefix` → error. The derived commit regex
   would be unverifiable, so onboarding fails instead of guessing.
2. `commits.format` declared with a value contradicting `management` → error,
   not a silent pass.
3. `harness.discipline: prd-first` with `harness.domains: false` → warning: the
   domain table is what carries the phase mapping.
4. `memory.committed_path` pointing outside the repository → error.
5. `version` greater than the binary understands → error: refuse to generate
   rather than guess a schema.
6. `rollout.mode: advisory` without `review_by` → error. Advisory is a transition
   state. An exemption with no expiry is drift that looks like compliance, because
   `check` reports and passes and nobody learns that the transition never ended.
7. Any `review_by` or exception date in the past → error, naming the rule it
   belongs to. Staying advisory past its date must be a deliberate renewal with a
   new date and a reason, never an omission.

## Behaviour

- **Detection, not dependency.** `dforge` reads `.dflow.yaml` when present and
  omits the workflow section when it is not. It never fails for missing optional
  context and never authors a `.dflow.yaml`.
- **Idempotence.** `dforge sync` regenerates derived artifacts from the schema.
  Delimited sections are replaced between their markers; a second run with no
  schema change produces no diff.
- **Never overwrite human edits.** Reusing `dflow/pkg/agent/reference.go`
  semantics: replace between markers, append when absent, and leave the file
  untouched when a marker is orphaned or a legacy heading is found.
- **The schema is the onboarding's memory.** Everything needed to regenerate is
  in the file, so `dforge sync` never asks again.

## Versioning

`version: 1` is required. A future schema change adds a new version with an
explicit upgrade path; `dforge` never rewrites an older schema in place without
being asked.

## Open

**Where do the review-budget numbers live for a team that disagrees?**
`600/400/2000` are `dforge` defaults, overridable per project. Whether they may
differ *within* one organization or become a locked organization floor is not
decided. The current position is per-project override, because a hard floor
applied to a legacy codebase would fail every check and teach the team to bypass
it.

## Evidence

- 17 `.dflow.yaml` files; the pattern is established and understood.
- `AGENTS.md:26-231`, in the Laravel application that keeps per-concern quality rule files — the Boost block, ~230 lines injected by another tool.
- `AGENTS.md:100`, in the Laravel application that keeps per-concern quality rule files — `.ai/rules/index.md` mapping file globs to rule files: a fifth location for rule content.
- `opencode.json`, in a Laravel API and web application — 325 lines of tool-managed configuration.
- `pkg/agent/reference.go:16-17`, `:35-39` — the marker semantics `dforge` reuses.
